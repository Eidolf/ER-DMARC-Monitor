= 01. Introduction and Goals

== Requirements Overview
The ER-DMARC-Monitor system ingests, parses, and visualizes DMARC (Domain-based Message Authentication, Reporting, and Conformance) aggregate reports.

== Quality Goals
* Reliability: Reliable processing of incoming DMARC XML reports via SMTP.
* Maintainability: Modular microservices architecture (API, SMTP Ingester, Parser).
* Usability: Clear dashboard interface for monitoring DMARC report metrics and domain health.

02-architecture-constraints.adoc

= 02. Architecture Constraints

== Technical Constraints
* Language / Environment: Python 3.10+ for backend services (`api/`, `dmarc-parser/`, `smtp-ingester/`), TypeScript/React/Vite for frontend (`frontend/`).
* Containerization: Docker and Docker Compose (`docker-compose.yml`).
* Data Stores: PostgreSQL database and Redis message queue / cache.

== Organizational Constraints
* Git Repository: Versioned under single monorepo layout.
* Open Source Standards: Standard license and documentation layout.

03-system-scope-and-context.adoc

= 03. System Scope and Context

== Business Context
The system interfaces with external Mail Transfer Agents (MTAs) sending DMARC aggregate reports via email.

== Technical Context
* Inbound Interfaces: SMTP Server (`smtp-ingester/main.py`) accepting incoming report emails.
* Processing Queue: Redis queue transferring raw/extracted payload to parser (`dmarc-parser/main.py`).
* Data API: FastAPI backend (`api/main.py`) exposing parsed metrics to web dashboard (`frontend/`).

04-solution-strategy.adoc

= 04. Solution Strategy

== Fundamental Decisions
* Decoupled Ingestion: Separate SMTP ingestion from XML parsing using Redis queues to handle spikes in email delivery.
* Asynchronous Parsing: `dmarc-parser` processes queued reports independently from API response cycles.
* Modern Web Interface: React SPA built with Vite for fast client rendering and analytics dashboards.

05-building-block-view.adoc

= 05. Building Block View

== Level 1: System Overview
The main system components include:
* `smtp-ingester`: Ingests incoming emails containing DMARC aggregate reports (`.zip`, `.xml`, `.gz`).
* `dmarc-parser`: Parses XML reports and inserts structured records into PostgreSQL.
* `api`: FastAPI application serving backend REST APIs (`api/main.py`).
* `frontend`: Single-page web application (`frontend/src/`).

== Level 2: Component Breakdown
* Database models & schemas defined in `api/` and shared ORM definitions.
* Background queue handlers in `dmarc-parser/`.

06-runtime-view.adoc

= 06. Runtime View

== Scenario 1: DMARC Report Ingestion & Processing
1. External MTA delivers DMARC report email to `smtp-ingester`.
2. `smtp-ingester` extracts attachment, pushes payload metadata to Redis queue.
3. `dmarc-parser` fetches job from Redis queue, decompresses XML, parses records, and saves to PostgreSQL.
4. User accesses frontend dashboard; `frontend` fetches aggregated metrics from `api`.

11-risks-and-technical-debt.adoc

= 11. Risks and Technical Debt

== Technical Risks
* Large XML Attachments: Processing extremely large aggregate reports could exceed container memory limits if not streamed.
* Malformed Email Reports: Handling non-standard DMARC XML schemas safely.

== Technical Debt
* Documentation Automation: AI updates must be validated manually by maintainers.
