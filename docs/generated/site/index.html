01. Introduction and Goals

Requirements Overview

The ER-DMARC-Monitor system ingests, parses, and visualizes DMARC (Domain-based Message Authentication, Reporting, and Conformance) aggregate reports.

Quality Goals

  • Reliability: Reliable processing of incoming DMARC XML reports via SMTP.
  • Maintainability: Modular microservices architecture (API, SMTP Ingester, Parser).
  • Usability: Clear dashboard interface for monitoring DMARC report metrics and domain health.

    03. System Scope and Context

    Business Context

    The system interfaces with external Mail Transfer Agents (MTAs) sending DMARC aggregate reports via email.

    Technical Context

  • Inbound Interfaces: SMTP Server (smtp-ingester/main.py) accepting incoming report emails.
  • Processing Queue: Redis queue transferring raw/extracted payload to parser (dmarc-parser/main.py).
  • Data API: FastAPI backend (api/main.py) exposing parsed metrics to web dashboard (frontend/).

    04. Solution Strategy

    Fundamental Decisions

  • Decoupled Ingestion: Separate SMTP ingestion from XML parsing using Redis queues to handle spikes in email delivery.
  • Asynchronous Parsing: dmarc-parser processes queued reports independently from API response cycles.
  • Modern Web Interface: React SPA built with Vite for fast client rendering and analytics dashboards.

    06. Runtime View

    Scenario 1: DMARC Report Ingestion & Processing

    1
    External MTA delivers DMARC report email to smtp-ingester (smtp-ingester/main.py).
    2
    smtp-ingester extracts attachment, pushes payload job metadata to Redis queue (smtp-ingester/main.py).
    3
    dmarc-parser fetches job from Redis queue, decompresses XML (.zip/.gz), parses records, and saves to PostgreSQL (dmarc-parser/main.py).
    4
    User accesses web dashboard; frontend fetches aggregated metrics via REST API endpoints (frontend/src/App.tsx, api/main.py).

    11. Risks and Technical Debt

    Technical Risks

  • Large XML Attachments: Processing extremely large aggregate reports could exceed container memory limits if not streamed.
  • Impact: Medium (Container OOM kill)
  • Likelihood: Low
  • Mitigation: Implement chunked streaming for decompressed XML payload parsing in dmarc-parser/main.py.
  • Detection: Monitor container memory utilization in Docker metrics.
  • Accountable Owner: Backend Lead (@dev-team)
  • Malformed Email Reports: Handling non-standard DMARC XML schemas safely.
  • Impact: Low (Parser task failure)
  • Likelihood: Medium
  • Mitigation: Wrap XML parsing in schema validation and catch parse exceptions explicitly in dmarc-parser/main.py.
  • Detection: Error log entries recorded in stderr.
  • Accountable Owner: Parser Maintainer (@dev-team)
